## Goal

Replace a scheduled Renovate CLI runner with a tool that updates the
dependencies of about a dozen repositories in seconds, not minutes.

Measured baseline (Renovate 44.155.6, warm caches, one EC2 c7i.large):

| | Time |
|---|---|
| Batch of 12 repos, before our release-notes patch | 6.7 min |
| Largest repository alone, after the patch | 44 s |
| Smallest repository alone, after the patch | 13 s |

Renovate's time went to processing one repository at a time with
per-repository caches, fetching full release and tag histories through
paginated APIs, re-parsing every changelog per version, and starting Node per
process. What remains is GitHub round-trips and lockfile tools, which no
language change removes.

## Principles

The user-facing [principles](/guide/how-it-works/#principles) apply. Inside the
engine they mean:

- Each lookup (data source and package) runs at most once per batch, however
  many repositories use the package.
- Release lists, tag lists and changelogs are stored with their validators
  (ETag, Last-Modified) and the newest item seen. A refresh fetches
  newest-first and stops at the first item already known.
- Repository files are read through the GitHub API at the default branch's
  commit, and commits are created through the API, signed by GitHub.
- If the default branch's commit and the resolved config are unchanged, the
  previous extraction is reused. If no new versions appeared either, no branch
  work happens.
- A stable, versioned JSON [report](/reference/report/) is the interface to
  callers. Logs are never parsed.

## Configuration

Pkl only, evaluated in-process with `pklr`. patchula publishes a typed
`PatchulaConfig.pkl` schema; a repository's config amends it, and an
organisation can share a base config through Pkl imports. There is no
`renovate.json` reader; [migrating](/renovate/migrating/) covers moving a
config by hand.

  - github/ REST and GraphQL client, App tokens, rate-limit governor
  - cache/ SQLite: HTTP entries, release lists, extraction fingerprints
  - http/ reqwest transport boundary, shared network pool
  - process/ external commands with an explicit environment and time limit
  - server/ GitHub App server over the engine
  - testkit/ dev-dependency only: redacted recording and offline replay
  - report/ versioned batch JSON caller contract, shared with conformance
  - cli/ `patchula` binary, defined with usage
- conformance/ Renovate comparison harness (black box only)

Async runtime: tokio. HTTP: reqwest with HTTP/2 and rustls. Errors and
diagnostics: miette. Terminal UI: ratatui, only on interactive terminals.

## Scope

GitHub only. Out of scope: other platforms, onboarding PRs, hosted services,
Docker-based tool installation, arbitrary post-upgrade commands and encrypted
config. The [compatibility matrix](/renovate/compatibility/) lists what is
supported.

## Run modes

One engine runs every batch, so a batch behaves the same however it started.
The CLI (`patchula run`, `patchula lookup`) runs one batch with a token the
caller supplies. The [server](/guide/server/)
(`patchula serve`) mints installation tokens from GitHub App credentials and
keeps its queue and caches warm. With `--remote`, the CLI signs in with the
server's App through GitHub's device flow, and the server runs the batch with
its own credentials once the user is shown to have push access.

Checkboxes say when a click takes effect: "re-check now" in server mode,
"re-check on the next run" in CLI mode. `--recheck now|next-run` (or
`PATCHULA_RECHECK`) overrides this for setups where a webhook receiver starts
CLI runs at once. A hidden marker, not the text, identifies the Count's
checkboxes.

Operator settings (sweep schedule, triggers, concurrency, re-check wording)
are a Pkl file separate from repository configs; see
[settings](/guide/server/#settings). Secrets, such as the App private key and
the webhook secret, never appear in settings and come only from environment
variables or files. There is no web UI and no settings managed by the Count
himself. Besides webhooks and health checks, the server has the `/api/v1` API
behind `--remote` and a read-only repository API for a separate dashboard.

## Tooling

All tools come from mise. Builds go through mr-boxington (`mbx`) locally and in
CI. The CLI is defined with usage, which also generates completions, Markdown
docs and the man page. Performance is tracked with tak, report-only for now.
Tests never touch the network: they replay responses recorded by patchula
itself.

Linting is hk, configured in `hk.pkl`. `mise run hooks:install` installs two
git hooks that run hk through mise:

- pre-commit fixes the staged files with rustfmt and `pkl format`, checks
  that `mise fmt` has nothing to change, and runs jactionlint and zizmor on
  the workflows, nu-lint on the nu file tasks and betterleaks on every staged
  file. Mark a test credential betterleaks reports with a trailing
  `// betterleaks:allow` comment on its line. nu-lint reads `nu-lint.toml`,
  where each rule group is either an error or off; silence a single finding
  with a `# nu-lint-ignore: <rule>` comment on the line before it.
- commit-msg rejects a message that is not a conventional commit, or that
  credits an AI tool in a trailer such as `Co-authored-by` or a "Generated
  with" line. The names and line patterns are lists at the top of
  `mise-tasks/lint/commits`.

`mise run lint` runs `hk check --all`: the pre-commit checks on the whole tree
plus Clippy, which is too slow for every commit. CI's lint job runs
`mise run lint:ci` instead, with `--from-ref`, so each step checks only the
files a push or pull request changed, and Clippy runs only when Rust sources,
Cargo files or `mise.toml` change. It turns the findings hk can place on a
line into annotations on the diff, and writes a job summary of every step.
A separate pull request check runs `mise-tasks/lint/commits` over every
commit, the title and the body, since a squash merge takes its message from
the title and credits each commit author after the local hooks have run.

This site is Astro Starlight, in `docs/`, served from Cloudflare Workers and
built from `main` with no per-release versions. `mise run docs:build` builds it
and `mise run docs:dev` serves it with live reload.
