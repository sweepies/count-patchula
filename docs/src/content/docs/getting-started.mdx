This page takes one repository from nothing to its first update pull requests.
You need a GitHub token, [mise](https://mise.jdx.dev) on the machine that runs
the Count, and about five minutes.

The fastest way is to have a coding agent do it. Give this prompt to an agent
working in your repository:

```text wrap
Fetch https://raw.githubusercontent.com/sweepies/count-patchula/main/docs/agent-setup.md and follow its instructions to set up Count Patchula for this repository.
```

The instructions it fetches have the agent check whether you use Renovate and
what carries over, ask how you want to run the Count, set him up, and migrate
your Renovate config. It asks before each decision, and never asks for your
secrets. The steps below do the same by hand.

<Steps>

1. ### Install patchula

   ```sh
   mise use -g packslip:sweepies/count-patchula
   patchula --version
   ```

   mise checks the download against the release's signed manifest. See
   [installation](/installation/) for release archives, Cargo, building from a
   checkout, and what the runner needs at run time.

2. ### Add a config to the repository

   The Count only visits repositories that invite him. Commit a `patchula.pkl`
   at the repository root:

   ```pkl
   // patchula.pkl
   amends "PatchulaConfig.pkl"

   prs { dashboard = true }
   ```

   That is a complete config. Everything else comes from the schema's defaults:
   every supported manager, exact version pins, digest pins for actions and
   images, a 24-hour release-age wait, one PR per update, and no auto-merge except
   for reference data such as CA root bundles.

   <Aside type="tip">
   `PatchulaConfig.pkl` does not need to exist in the repository. When the Count
   reads a config he supplies the schema himself. Vendor it if you want completion
   in an editor, and check the config locally:

   ```sh
   patchula config schema > PatchulaConfig.pkl
   patchula config check .
   ```
   </Aside>

3. ### Get a token

   Export a token in `PATCHULA_TOKEN` (`GITHUB_TOKEN` and `GH_TOKEN` also work).
   With none of them set, the Count asks a signed-in [GitHub
   CLI](/guide/how-it-works/#tokens) for its github.com token.

   - For `lookup` and dry runs, any token that can read the repository is enough.
   - For real runs, use a GitHub App installation token. Commits are created
     through the API so GitHub signs them, and the Count checks that branches he
     touches only contain his own verified commits. The App needs contents, pull
     requests, issues and workflows write access, plus read access to checks and
     commit statuses.

   Long-running setups can let the Count mint installation tokens himself. See
   the [GitHub App server](/guide/server/).

4. ### Look before you leap

   ```sh
   patchula lookup --json acme/my-app > report.json
   patchula run --dry-run acme/my-app
   ```

   `lookup` prints a summary and writes the [JSON report](/reference/report/): every
   dependency found, its current version and the proposed updates. `run --dry-run`
   goes further and prints the branches, files and diffs it would publish,
   without touching GitHub.

5. ### Run it

   ```sh
   patchula run acme/my-app
   ```

   The first run opens one PR per update and, with `dashboard = true`, a
   Dependency Dashboard issue. Lockfiles are regenerated with the real tools,
   which mise installs on first use into a tool store kept beside the cache. Run
   the same command again and the Count notices nothing changed: an unchanged
   repository costs one GraphQL query on the write side.

   Without a repository argument, `lookup` and `run --dry-run` read the working
   tree in the current directory, uncommitted changes included. A real `run`
   opens PRs for the checkout's repository on github.com (its `origin` remote, or
   its only remote), and only once the working tree is clean and at the remote's
   default branch. Pass `--all-repos` to process every repository the token can
   reach.

   To run him on a schedule, use the [GitHub Action](/guide/github-actions/).

</Steps>

## Run him as a server

Once you are happy with what he proposes, run the [GitHub App
server](/guide/server/). It is the recommended way to run the Count: one
long-running process keeps every cache warm between batches, batches work from
many repositories together, and reacts to webhooks, so a ticked checkbox on one
of his PRs or the dashboard is acted on straight away instead of at the next
scheduled run. It sits idle most of the time, which makes usage-billed hosts
such as [Railway](/guide/server/#hosting-on-railway) cheap to run it on.
