This page takes one repository to its first update pull requests. You need a
GitHub token and [mise](https://mise.jdx.dev).

The fastest way is to give a coding agent in your repository this prompt:

```text wrap
Fetch https://raw.githubusercontent.com/sweepies/count-patchula/main/docs/agent-setup.md and follow its instructions to set up Count Patchula for this repository.
```

The agent checks for a Renovate config to migrate, asks how you want to run the
Count, and sets him up. It asks before each decision and never asks for
secrets. The steps below do the same by hand.

<Steps>

1. ### Install patchula

   ```sh
   mise use -g --minimum-release-age 0 packslip:sweepies/count-patchula
   patchula --version
   ```

   mise verifies the download against the release's signed manifest. Other
   options are under [installation](/installation/).

2. ### Add a config

   The Count only visits repositories that invite him. Commit a `patchula.pkl`
   at the repository root:

   ```pkl
   // patchula.pkl
   amends "PatchulaConfig.pkl"

   prs { dashboard = true }
   ```

   That is a complete config; the rest comes from the schema's defaults: every
   manager, exact pins, digest pins for actions and images, a 24-hour
   release-age wait, one PR per update, and no auto-merge except for reference
   data such as CA bundles.

   <Aside type="tip">
   You don't need to commit `PatchulaConfig.pkl`; the Count supplies it. Vendor
   it for editor completion, and check the config locally:

   ```sh
   patchula config schema > PatchulaConfig.pkl
   patchula config check .
   ```
   </Aside>

   No config yet? In a checkout without one, `lookup`, `tui` and
   `run --dry-run` offer to use the defaults or write a starter file. Without a
   terminal, pass `--default-config`.

3. ### Get a token

   Export `PATCHULA_TOKEN` (or `GITHUB_TOKEN` or `GH_TOKEN`). With none set,
   the Count uses a signed-in [GitHub CLI](/guide/how-it-works/#tokens)'s token.

   - `lookup` and dry runs need any token that can read the repository.
   - Real runs need a GitHub App installation token, so GitHub signs the
     commits. The App needs write access to contents, pull requests, issues and
     workflows, and read access to checks and commit statuses.

   The [GitHub App server](/guide/server/) can mint installation tokens itself.

4. ### Look before you leap

   ```sh
   patchula lookup --json acme/my-app > report.json
   patchula run --dry-run acme/my-app
   ```

   `lookup` writes the [JSON report](/reference/report/) of dependencies and
   proposed updates. `run --dry-run` prints the branches and diffs it would
   publish, without touching GitHub.

5. ### Run it

   ```sh
   patchula run acme/my-app
   ```

   The first run opens one PR per update and, with `dashboard = true`, a
   Dependency Dashboard issue. Lockfiles are regenerated with the real tools,
   which mise installs on first use. A repeat run on an unchanged repository
   costs one GraphQL query.

   With no repository named, `lookup` and `run --dry-run` read the working
   tree here, uncommitted changes included. A real `run` opens PRs for the
   checkout's github.com repository, once the tree is clean and at the remote's
   default branch. `--all-repos` processes every repository the token can
   reach.

   To have the updates written into your checkout instead of opened as PRs, run
   [`patchula apply`](/guide/apply/) there, or pick them one by one in the
   [terminal UI](/guide/tui/).

   To run him on a schedule, use the [GitHub Action](/guide/github-actions/).

</Steps>

## Run him as a server

The recommended way to run the Count is the [GitHub App
server](/guide/server/). It keeps caches warm, batches many repositories
together, and acts on webhooks, so a ticked checkbox is handled straight away
rather than at the next scheduled run. It idles most of the time, so
usage-billed hosts such as [Railway](/guide/server/#hosting-on-railway) are
cheap.
